### Drill A — staged bad deploy: session before user-visible failure

Deployment `drill-a/webapp`: 2 replicas of `python:3.12-alpine` running
`http.server` behind Service `drill-a/webapp`, readiness probe on `/`,
strategy `maxUnavailable=0 maxSurge=1` — the shape where a bad deploy
CANNOT hurt users as long as somebody notices before it proceeds. Baseline
curls through the Service from an in-cluster prober pod: HTTP 200.

**10:51:41** the bad deploy: image bumped to `python:3.13-alpine` with a
crashing command (valid image, exits 1 — readiness never passes). The
surge pod crash-loops; the two old-revision pods keep serving.

Timeline (sentinel log, run 1 — everything at shipped default severities):

```
10:51:47 fire BackOff pod=drill-a/webapp-55866d5cff-cwgp4 → sid=stub-sess-0004   (reactive, pod-level, +6s)
10:52:02 fire Unhealthy pod=drill-a/webapp-55866d5cff-cwgp4 → sid=stub-sess-0005
10:54:55 watchboard: buffered rollout.stall drill-a/webapp (severity=warning)    (leading, Deployment-level, +3m14s)
10:55:59 watchboard: digest 1 entry(ies) → sid=stub-sess-0009
10:58:24 kubectl rollout undo
10:58:40 resolved rollout_stall drill-a/webapp → sid=stub-sess-0009 (resolution=recovered)
```

**The race**: `rollout.stall` fired at onset+3m14s (`--rollout-observe`
default 3m — evidence-based: `new_ready=0/1 old_ready=2/2`).
`objectstate.progress_deadline` would fire at 80% of the default
`progressDeadlineSeconds` (600s), i.e. onset+8m — **rollout.stall won by
~4m46s** and progress_deadline never got to fire before the rollback.
The reactive pod-level events (BackOff at +6s) are earlier but name the
wrong object at the wrong altitude: a crashing pod, not a stalled
Deployment; the stall signal is the one that says "probable bad deploy,
old revision healthy" — and it deduped separately by design (workload
UID, reason `rollout_stall`).

**No user-visible failure, proven during the stall** (10:54:41, between
the stall firing and the rollback — captured in the drill record):

```
HTTP/1.0 200 OK   × 5    (Server: SimpleHTTP/0.6 Python/3.12.13 — the OLD revision)
webapp-55866d5cff-cwgp4   0/1   CrashLoopBackOff   4
webapp-77f8d7558c-7gvwx   1/1   Running            0
webapp-77f8d7558c-c2nmj   1/1   Running            0
```

Run 1 exercised the DEFAULT routing: `rollout.stall` is warning-class, so
it landed in the watchboard board session (stub-sess-0009), and its
`kind=resolved` (resolution=recovered) followed into the same session
16 seconds after the `rollout undo`. For the criterion's strong reading —
a session of its own — **run 2** repeated the drill with the §7.7
severity knob turned the other way (`--severity=rollout.stall=critical`,
the "staging cluster, bad deploys page" judgment; sentinel restarted at
11:08 to apply it):

```
11:09:12 bad deploy #2 applied (new revision, crashing command)
11:12:22 enrich drill-a/webapp: 3019B (outcome=ok, sections=4)
11:12:22 fire rollout_stall pod=drill-a/webapp → sid=stub-sess-0019    (+3m10s, own session, enriched)
11:13:18 curls through the Service: 5 × HTTP/1.0 200 OK (old pods 2/2, new pod CrashLoopBackOff)
11:13:32 kubectl rollout undo
11:13:52 resolved rollout_stall → sid=stub-sess-0019 (resolution=recovered)
```

The initial inject is the frozen payload shape with the full 4-section
enrichment bundle attached; the message carries the §7.2 evidence
verbatim: `rollout stalled: new ReplicaSet webapp-6cfdc68df new_ready=0/1
old_ready=2/2 elapsed=3m10s — new-revision pods failing while the old
revision stays healthy (probable bad deploy, fired ahead of
progressDeadlineSeconds)`.

A session opened 3m10s after the bad deploy; users saw 200s the entire
time; the rollback produced a schema-stable outcome record in the same
session. (The resolved record's duration fields are off — observation 4.)

### Drill B — staged memory leak: forecast before the OOM kill

Pod `drill-b/leaker`: 64Mi memory limit, running
[`dev/drills/memory-leaker.py`](../../dev/drills/memory-leaker.py) —
+1 MiB of touched pages every 30s (~1.6% of the limit per sample
interval), started **10:50:27**.

```
10:56:25 watchboard: buffered saturation.forecast drill-b/leaker (severity=warning)   (+5m58s)
         pod at signal time: phase=Running ready=True restarts=0 (17Mi/64Mi)
11:05:56 fire forecast_memory pod=drill-b/leaker → sid=stub-sess-0010                 (+15m29s, critical escalation)
         pod at signal time: phase=Running ready=True restarts=0
11:20:04 OOMKilled (restartCount 0→1) — the FIRST failure marker of any kind
```

The warning forecast fired once the sample span crossed half the window
(§13's insufficient-window gate released at ~6 min, as tuned), while the
pod was Running and Ready with zero restarts — nothing reactive existed
to see. The warning→critical escalation (ETA under 15m) opened the
per-incident session; its wire payload (captured verbatim):

```json
{"kind":"saturation.forecast","reason":"forecast_memory",
 "namespace":"drill-b","kind_of_object":"Pod","name":"leaker","container":"leaker",
 "message":"memory saturation forecast for leaker: current=34.8MiB limit=64.0MiB slope_per_min=2.0MiB — limit reached in ~14m39s at the observed trend (20 samples over 10m0s)",
 "cluster":"kl-m3","context":{"node":"kl-m3-worker"},
 "forecast":{"eta":"2026-07-26T11:20:35.49782084Z","confidence_basis":"linear-10m-window"}}
```

The kernel OOM-killed the container at **11:20:04** — the forecast issued
14m08s earlier predicted **11:20:35**, an error of 31 seconds. Margins:
**warning 23m39s before failure, critical session 14m08s before failure**;
at both signal instants the pod was Running/Ready/0-restarts (captured).
(`confidence_basis` reads `linear-10m-window` because the drill runs
`--saturation-window=10m`; the production default emits the §8
`linear-90m-window` — same basis string, parameterized.)

Unplanned bonus, same run: deleting a webapp pod during drill C's
topology-change step dropped the Service's ready ratio 2/2→1/2, and the
**degradation source** fired `degradation.capacity` (critical at
surviving ratio ≤ 0.5) with the §7.2 step timeline in the message
(`ratio 1.00→0.50, drop 0.50 ≥ 0.30, downward steps 2 ≥ 2 … timeline:
2/2 → 2/3 → 2/2 → 1/2`) into its own session — and resolved it
7m16s later when the replacement pod came Ready. Three of the four new
sources fired live in this drill; expiry scanned honestly (kind's
year-long certs sit outside the 14d warning window; the cert-manager
skip logged loudly).

### Drill C — blast radius at onset, ~29 minutes after the fact

Onset: drill A's stall at **T = 10:54:55**. After the fact, the cluster
moved on: rollback 10:58:24 (broken ReplicaSet scaled to 0, pod deleted),
a healthy neighbor pod deleted and replaced 11:15:05, the leaker OOM'd —
dozens of snapshot intervals elapsed. The store (SQLite + WAL, 3.7 MB)
was then copied OFF the node and queried on the host with no cluster
access on the query path (`source=history` below is the offline proof).

The distroless sentinel image has no tar, so `kubectl cp` cannot reach
the store; the drill mounts `--store` on a hostPath and copies with

### Verdict

Exit criterion met, measured: the staged bad deploy opened a session
**3m10s after the rollout while every user request returned 200** (the
old revision kept serving; the failure never became user-visible and was
rolled back to a `kind=resolved` record 90 seconds later); the staged
memory leak opened a critical session **14 minutes before the OOM kill**
(warning signal 23m39s before; forecast ETA accurate to 31 seconds) while
the pod was Running and Ready with zero restarts; and "blast radius at
onset" was answered **28m34s after onset, offline, from the copied
store** — showing the broken-revision topology the live cluster had
already forgotten, with the bad rollout named as the last change before
onset.

## Observations and gaps found by the drill (not fixed in this PR)

1. **`store.GraphAt` cannot replay across a sentinel restart.** The
   snapshot generation sequence and interned NodeIDs reset per process,
   but the delta log is continuous in the store — a query whose replay
   window crosses the restart fails with `graph: bad change effect:
   nodeNew 70: key "ReplicaSet/…" does not match interned
   "Deployment/…"`, and any `--at` after the restart is unanswerable
   from a store carrying pre-restart history. Restarts are routine
   (upgrades, evictions); the change log needs an incarnation marker (or
   the replayer needs to re-anchor at the first post-restart snapshot).
2. **History-mode radius loses the #46 unknown-vs-missing fix.**
   Store-restored snapshots claim `radius.missing
   reason=ReferencedNotFound` for identity-only neighbors (the drill's
   `Deployment/webapp`, `ConfigMap/kube-root-ca.crt`) that the live-graph
   path correctly renders as `observed=unknown` — `Snapshot.Watches`
   appears not to survive Encode/Restore, regressing historical answers
   to the pre-#46 mislabeling.
3. **Historical queries cannot target a Deployment.** The sentinel graph
   feed holds Deployments identity-only (via ReplicaSet ownerRefs), so
   `triage radius|changes --workload=Deployment/… --at=…` fails with
   "not found in the topology" at ANY instant, even though the same
   target works live. Post-mortems must center on the Pod or ReplicaSet
   (as this drill did). Either ingest Deployments into the graph feed or
   resolve Deployment targets through their owned ReplicaSets.
4. **`rollout_stall` resolved records bypass the stability window and
   invert their durations.** Both runs resolved 16–20s after the
   rollback despite `--recovery-stable-for=60s`, with `cleared_after=0s`
   (the stall had persisted 3m29s) and `observed_stable_for` counted
   from FIRE time (`3m44s` / `1m29s`) rather than clearance time — the
   rollout clearance observer appears to stamp `StableSince` at fire
   time, which both skips the debounce and corrupts the §9.3 corpus
   fields.
5. **Minor: informer-sync Adds masquerade as changes.** The delta log
   records every object observed at graph start as `Added` at the sync
   instant, so a `triage changes` window spanning a sentinel (re)start
   reports pre-existing objects as changes (`Node kl-m3-worker
   reason=Added` in drill C's output). An `origin=sync` marker (or
   suppressing sync-Adds like EndpointSlice churn) would keep the
   timeline honest.
