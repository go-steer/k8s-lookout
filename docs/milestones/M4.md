# M4 — capacity & quota: completion record and exit-check evidence

Milestone per [DESIGN.md §14](../DESIGN.md). Completed 2026-07-26.

## Exit criterion

> Staged quota exhaustion yields correlated incident + drafted increase
> request; a health scan run mid-incident reports the triage state, not
> a fresh unknown.
> — DESIGN.md §14, M4 row

Session policy for this run (recorded up front, per the standing
decision): **no live GCP.** The §13 testing conventions already commit
GCP checks to recorded/scripted fixtures behind the `pkg/cloud` client
interfaces; the exit checks below run the REAL merged pipeline over
those seams, plus a kind cluster wherever the Kubernetes half is real.
The real-project replay procedure is
[`dev/drills/quota-exhaustion.md`](../../dev/drills/quota-exhaustion.md),
which maps every fixture to the API it stands in for.

## Exit check A — staged quota exhaustion → correlated incident + draft

### A.1 The full pipeline, engine level (fixtures per policy)

`internal/watch/quota_drill_test.go`
(`TestDrill_QuotaExhaustion_CorrelatedIncidentWithDraft`, added by this
PR) runs the REAL `quota` and `capacity` sources — constructed through
their shipped `New` paths, provider-boundary checks included — over
scripted cloud APIs, into the REAL dispatcher (filter → §7.7 routing →
dedup → watchboard/per-incident sessions → inject) against the fake
daemon, with wall-clock compressed via the poll knobs and a short dedup
window. Scripted sequence: CPUS/us-east1 at 85% growing 50/day (ETA
~6d), then 98% growing 60/day (ETA ~16h), then a `GCE_QUOTA_EXCEEDED`
noScaleUp decision naming the same quota. Captured on the wire
(2026-07-26 run, verbatim):

**Step 1 — the warning forecast does NOT page** (watchboard digest,
own session):

```json
{"kind":"watchboard.digest","cluster":"kl-m4-drill","board_generation":1,"sequence":1,
 "entries":[{"kind":"quota.forecast","fingerprint":"sha256:5641…bdee","reason":"quota_forecast",
 "kind_of_object":"Quota","name":"CPUS","uid":"quota:CPUS/us-east1","count":1,…}]}
```

**Step 2 — the critical escalation opens the incident session, draft
attached** (the §10.3 deliverable, one inject):

```json
{"kind":"quota.forecast","reason":"quota_forecast","kind_of_object":"Quota","name":"CPUS",
 "uid":"quota:CPUS/us-east1",
 "message":"quota CPUS in us-east1 at 98.0% (usage 1960 / limit 2000), growing 60/day over the last 7d (8 points) — exhausted in ~16h0m0s at current slope; drafted increase to 3000 attached — file it via core-agent's permission gate",
 "cluster":"kl-m4-drill",
 "forecast":{"eta":"2026-07-27T04:42:06Z","confidence_basis":"linear-7d-window"},
 "quota_increase_draft":{
   "quota_id":"compute.googleapis.com/cpus","region":"us-east1",
   "current_usage":1960,"current_limit":2000,
   "suggested_limit":3000,"slope_per_day":60,
   "justification":"CPUS in us-east1 is at 1960 of 2000 (98.0%). Usage grew 60/day over the observation window; at that slope the quota is exhausted in ~16h0m0s (around 2026-07-27). Requesting an increase to 3000 to cover twice the expected request turnaround at the observed growth."}}
```

The test pins the draft against the documented formula
(`pkg/sources/quota/draft.go`): `suggested = ceil(max(2000×1.5,
1960 + 2×60×7)) = 3000`, slope and justification asserted from the
same numbers the forecast fired on.

**Step 3 — the reactive scaleup failure is the SAME incident.** The
capacity source's decision (`Quota 'CPUS' exceeded. Limit: 2000.0 in
region us-east1.`) re-keys to `quota:CPUS/us-east1`; the
`QuotaExhausted` family folds it into the open session:

```
dedup quota_blocked pod=/mig-prod-a (count=2, window active)
store: kind=capacity.quota_blocked canonical_reason=QuotaExhausted
       route=suppressed session_id=sess-xx     ← the critical forecast's session
```

Final ledger: exactly 2 injects (warning digest + critical incident),
2 sessions, zero re-fires across a further poll of the same critical
state (the hysteresis latch), and `dedup.LookupSession(quota_blocked)`
resolving to the forecast's session. One diagnosed incident, not two —
asserted, not narrated.

## Exit check B — a health scan mid-incident reports the triage state

Same kind cluster, full loop, no fixtures anywhere.

**1. The incident.** Deployment `triagelab/checkout` (busybox printing
`FATAL: connection string invalid: postgres://…` and exiting 1)
crash-looped; the sentinel opened per-incident session
`stub-sess-0004` at 12:46:51 (`fire BackOff
pod=triagelab/checkout-697567895d-2gglt`).

**2. The agent writes the diagnosis.** DESIGN.md §9.4 has the incident
agent write the record through the shared Memory interface — which
core-agent v2.7.0 does not ship, and lookout deliberately exposes **no
CLI/MCP write command** for (documented in `pkg/store/memory.go`: a
new §4.1 command group needs a design-doc change first). **Finding 1
below.** The drill's stand-in is
[`dev/drills/write-triage-status`](../../dev/drills/write-triage-status/main.go)
(added by this PR): a ~100-line fixture that writes through the same
`pkg/memory` contract the real path will use, fingerprint computed
exactly as the sentinel stamps it. Executed on the node against the
LIVE store (WAL absorbed the concurrent writer; the sentinel never
blinked):

```
wrote triage-status record:
  fingerprint  sha256:e2957792a0b3ad9e29db2051dbc69ff01dfe3a52da8dbb6d1331aa44fe946f8b
  resource_key Pod/triagelab/checkout-697567895d-2gglt
  status       triaged           severity_override=warning
  root-cause   "DB connection string invalid in checkout-config (…)"
  action       "fix PR opened; config rollout pending — traffic on old revision unaffected"
  session      stub-sess-0004
```

**3. The scan, mid-incident.** `lookout health` from a host copy of
the live store (pod still crash-looping, restarts=4). WITHOUT the
store — the fresh unknown the criterion forbids:

```
kind=health.category severity=critical category=crashloops status=degraded total=1 …
kind=pod.crashloop severity=critical namespace=triagelab kind_of_object=Pod
  name=checkout-697567895d-2gglt reason=CrashLoopBackOff container=busybox
  restarts=4 last_state=Error exit_code=1
```

WITH `--store` — the §9.4 deliverable, verbatim:

```
kind=health.category severity=warning category=crashloops status=degraded total=1 …
kind=pod.crashloop severity=warning namespace=triagelab kind_of_object=Pod
  name=checkout-697567895d-2gglt reason=CrashLoopBackOff container=busybox
  restarts=4 last_state=Error exit_code=1
  triage_status=triaged
  triage_root_cause="DB connection string invalid in checkout-config (postgres://checkout@db:5432 — secret rotated, deploy not restarted)"
  triage_action="fix PR opened; config rollout pending — traffic on old revision unaffected"
  triage_session=stub-sess-0004 triage_age=1m21s
```

Diagnosis, paper trail, the agent's severity judgment — and the
category scorecard downgraded with it (critical → warning at the
scorecard line too, so "any issues?" reflects triaged reality).

**4. Followups stop re-paging.** Sixteen seconds after the write (30s
cache, §9.4), every subsequent signal for the incident logged the
override:

```
12:48:17 triage-status: downgraded k8s-event triagelab/checkout-697567895d-2gglt
         critical → warning (status=triaged, session=stub-sess-0004)
```

Within the dedup window, followups kept deduping into `stub-sess-0004`
(the binding IS the §9.4 attach flow). The re-page path — a fresh
dedup cycle for the same incident — was then forced with a 45s drill
window (kubelet's steady-state BackOff cadence of ~60–75s never lets
the shipped 5m window lapse; observation 3): the re-fire was
classified warning by the record and routed to the WATCHBOARD, not a
page —

```
13:12:30 triage-status: downgraded k8s-event triagelab/checkout-697567895d-2gglt
         critical → warning (status=triaged, session=stub-sess-0004)
13:12:30 watchboard: buffered k8s-event triagelab/checkout-697567895d-2gglt
         (severity=warning, buffered=1/5)
13:13:32 watchboard: digest 2 entry(ies) → sid=stub-sess-0006
```

— and the digest entry carries the record's exact fingerprint
(`sha256:e2957792…`). Stub ledger for the whole drill: after
`stub-sess-0004`, NO further per-incident session for the crashloop;
only watchboard digests.

## Verdict

Exit criterion met, both halves, with the GCP seam fixture-driven per
the recorded session policy: staged quota exhaustion produced ONE
correlated incident whose opening inject carries the drafted increase
request with formula-exact values (engine level, real sources, real
dispatcher, asserted in CI forever via the new drill test), and the
same dedup-family join was demonstrated live in kind on the portable
capacity seams (three angles, one session, store-audited); a health
scan run mid-incident returned the diagnosis, action, session pointer,
and downgraded severity instead of a fresh critical unknown, and the
sentinel honored the same record by routing the incident's next dedup
cycle to the watchboard instead of re-paging.

## Observations and gaps found by the drill (not fixed in this PR)

1. **No agent-facing write path for triage-status records.** §9.4's
   writer is the incident agent, but core-agent ships no Memory
   surface and lookout has no CLI/MCP/API write command (deliberate —
   `pkg/store/memory.go` documents that a write command is a §4.1
   design-doc change). Until one exists, nothing outside a Go program
   linking `pkg/store` can write a record; the drill needed the
   `dev/drills/write-triage-status` stand-in run ON THE NODE. This is
   the milestone's biggest seam: the feature is consumer-complete
   (routing, health, bundle, lifecycle all work) but producer-blocked
   for real agents. Decide the surface (likely `lookout memory
   triage-status set …` + an MCP tool behind the daemon's caller
   identity) in a design-doc change early in M5.
2. **The shipped ClusterRole breaks enrichment's scoped-list path.**
   Every enrichment in this run failed at the resolve stage:
   `enrichment_error stage=resolve error="listing daemonsets:
   daemonsets.apps is forbidden…"` (`outcome=failed, sections=0` on
   all 5 enriched incidents). This sentinel ran WITHOUT `--storm`, so
   enrichment used its `scoped-list` read path, which builds the
   incident namespace's workload snapshot by listing all workload
   kinds — including DaemonSets and Jobs, which `deploy/12` never
   grants (`apps`: deployments/replicasets/statefulsets only). The
   M2/M3 drills all ran `--storm`, whose live-graph resolve path
   masked the gap (`outcome=ok, sections=4` there). Either grant
   `daemonsets`+`jobs` list in the ClusterRole or degrade the
   scoped-list collector per-kind instead of failing the section; a
   §13-style RBAC probe over the enrichment path would have caught it
   at startup.
3. **Steady crashloops never leave the dedup window.** kubelet emits
   `BackOff` roughly every 60–75s at the 5m backoff cap, so with the
   shipped `--dedup-window=5m` (and even the drill's 2m) the window
   never expires and the §9.4 "re-page" path only triggers after an
   actual quiet period. Correct behavior (the incident IS still
   bound), but worth knowing when reading §7.7: for a persistent
   crashloop the override's visible effect is the per-signal
   downgrade log + the store severity, not a routing change, until
   the loop pauses. The drill demonstrated the routing change with a
   45s window.
4. **The joined reactive signal is invisible inside the session.**
   The `quota_blocked` (and `capacity.pending`) family joins are
   dedup-suppressed: recorded in the store with the session id, but
   no followup inject — the agent working the forecast session never
   hears "the autoscaler just hit this for real" unless it polls the
   store. M2 storms solved the same problem with `kind=storm.member`
   followups. Consider a low-rate `kind=family.member` followup for
   cross-SOURCE dedup joins (leading↔reactive), which is §9.3-relevant
   evidence too.
5. **Project-tier quota deployment needs a tagged image.** The
   published default image is GCP-free by design (§2 conformance
   test), so `--sources=…,quota` in it refuses at startup (correct,
   loud). But the deploy/ manifests offer no project-tier variant and
   GHCR publishes no `-gke` flavor, so the runbook builds its own.
   Decide the release artifact (second image tag vs `allproviders`
   default) before M5's fleet work multiplies deployments.
