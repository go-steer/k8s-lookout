# Adding a check

A *check* is one read-path command: `lookout audit netpol`, `lookout state
volumes`, `lookout triage delta`. This document walks one real check end to
end and then lists the touchpoints, so that the answer to "how do I add a
check" is a file rather than a person.

The short version:

```console
$ dev/tools/new-check --group=state --check=quotas \
    --summary="When creates are rejected with 'exceeded quota': which ResourceQuotas are at their limit ..."
```

That writes `pkg/checks/state/quotas.go`, `quotas_test.go` and
`testdata/quotas.golden`, registers the command, and runs the generated golden
test to prove the scaffold compiles. What comes out is a working command that
finds nothing. Everything below is about turning it into one that finds
something, and only something.

## 1. The contract you are joining

Every command is one `checks.Command` value, registered at init time. That one
declaration is the source for five surfaces:

| Surface | Generated by |
| --- | --- |
| `lookout <cmd> --help` | `Command.Help()`, at runtime |
| The MCP tool schema | `internal/mcpserver`, at runtime |
| `skills/*/references/*.md` | `dev/tools/gen-skill-refs` (committed; a drift test fails if stale) |
| `docs/site/.../reference/*.md` | `dev/tools/gen-site-docs` (committed; same) |
| The finding-kind glossary | `Registry.KindGlossary()` → `reference/finding-kinds.md` |

So there is nothing to hand-write twice, and nothing to keep in sync — but the
declaration has to be complete, because a field left empty is a hole in five
places at once. `checks.Register` calls `Command.Validate()` and **panics** on
an invalid declaration: an unknown group, a non-snake_case MCP name, a
multi-line summary, an output field that shadows an envelope key, a finding
kind that is not `<owner>.<slug>`. That panic is at init, so a bad declaration
fails every test in the tree rather than one.

## 2. Deciding the claim before writing the code

The hard part of a check is not Go. It is stating, in one sentence, a claim
that is **true, actionable, and silent when the cluster is fine**:

- **True.** Whatever the check reports has to be something the API actually
  says, not something correlated with it. If the claim needs a heuristic
  threshold, that threshold is a flag with a defensible default, and the
  rationale comment says what the default is defending.
- **Actionable.** A finding that does not imply a next step is noise with a
  severity attached.
- **Silent when healthy.** §1.5: healthy resources are omitted. A check that
  fires on a normally-configured cluster will be turned off, and then the
  checks around it lose credibility too.

Every rule worth writing has a legitimate look-alike. Before writing the
detector, write down the look-alike and how you will exclude it. `audit netpol`
excludes `hostNetwork` pod templates because NetworkPolicy selects pods and a
pod on the node's network stack is not one it can constrain — no policy an
operator could write would clear the finding, so reporting it would be a lie
with a remedy attached. That exclusion is not silent: the count comes back out
as `host_network_workloads`.

## 3. `audit netpol`, end to end

`pkg/checks/audit/netpol.go` is the model to copy. It is 458 lines, better than
a quarter of them prose, and the proportion is deliberate.

### 3.1 The rationale comment

The doc comment on the `…Command` constructor is the check's spec. It answers
four questions in order, and reviewers will ask for them if they are missing:

1. **What exactly does the claim mean?** *"A pod is isolated for a direction
   when some NetworkPolicy in its namespace selects it AND names that direction
   in policyTypes."*
2. **What is deliberately out of scope?** *"A policy whose rule is `ingress:
   [{}]` isolates the pod and then allows the whole cluster back in; this check
   counts it as coverage."* Naming the limit is what keeps the check from
   being read as a stronger guarantee than it is.
3. **Why this subject?** netpol emits against the *namespace* when nothing in
   it is covered and against the *workload* when its neighbours are covered and
   it is not — one decision and one remedy get one finding, a per-template
   mistake gets one each.
4. **Why these severities?** Unrestricted ingress is a warning (lateral
   movement); unrestricted egress is info (widely not adopted, and a fleet that
   chose not to do egress policy should not read as a fleet of warnings).

### 3.2 Kinds and reasons

Two constants, two different jobs:

```go
// kindNetpolMissing is the one condition this detector reports.
const kindNetpolMissing = "audit.netpol_missing"

const (
	reasonNoIngressPolicies         = "NoIngressPolicies"
	reasonIngressPoliciesSelectNone = "IngressPoliciesSelectNothing"
	reasonUnselectedIngress         = "UnselectedIngress"
	// …
)
```

The **kind** is the stable vocabulary a consumer filters and a fingerprint is
built from. It is `<owner>.<slug>`, lowercase snake_case both halves, and it
belongs in the `Kinds` ledger on the command:

```go
Kinds: []checks.KindField{
	checks.Kind(kindNetpolMissing,
		"nothing restricts this direction for the subject — a namespace with no policy at all, or a workload the covering policies' selectors miss; info for the egress direction, where no policy is a defensible default",
		emit.SeverityWarning, emit.SeverityInfo),
},
```

Two tests hold that ledger to the code. `checktest.Verify` (which every
contract test runs) rejects a finding whose kind is not declared or whose
severity is not among the declared ones, and
`pkg/checks/all/kinds_test.go` sweeps the *source* of every check package for
kind literals and fails on one that never reaches a ledger. Prefer a few broad
kinds with many reasons over a kind per condition: the kind is the API, the
reason is the detail.

The **reason** is CamelCase, like a Kubernetes condition reason, and it is
where the sub-cases live. Reasons are not validated — they are documented by
the kind's ledger doc and by the messages.

### 3.3 The `Output` glossary

Every detail key a finding can carry is declared, with a sentence saying what
it means and — this is the part people skip — what its zero and omitted cases
mean:

```go
{Name: "policies", Doc: "NetworkPolicies in the namespace naming this direction in policyTypes; 0 on a namespace-subject finding, and the number that failed to select the subject on a workload one"},
{Name: "host_network_workloads", Doc: "pod templates excluded because they use the node's network namespace, where NetworkPolicy does not apply; omitted at 0"},
```

Summary notes go in the same glossary (`namespaces` above is one). Envelope
keys — `scanned`, `findings`, `elapsed`, and the finding fields themselves —
are implicit and re-declaring one is a validation error.

### 3.4 The summary line

`Summary` is the single most-read string in the declaration: it is the MCP tool
description, so it is what a model reads when deciding whether to call this
tool at all. Write *when to reach for this*, not *what it does*, and end with
what `scanned` counts. netpol's runs to five sentences and that is fine.

### 3.5 Scope, flags, and exit codes

Scope errors are **usage** errors, exit 2, and they say what to do instead:

```go
if !inv.Scope.Workload.IsZero() {
	return 0, emit.UsageErrorf("audit netpol judges a workload against the policies of the whole namespace around it, so it is scoped by namespace: use --namespace=%s or -A", inv.Scope.Workload.Namespace)
}
if inv.Scope.Namespace == "" && !inv.Scope.AllNamespaces {
	return 0, emit.UsageErrorf("no scope: pass --namespace=<ns> or -A")
}
```

`emit.UsageErrorf` is what makes it exit 2. A bare `fmt.Errorf` exits 1, which
tells a caller "the cluster or the tool broke" when the truth is "you passed
the wrong flag" — and exit 1 is the one an agent retries. The distinction is
per-command and nothing sweeps for it, so it is on you and your reviewer: a
malformed invocation exits 2, a well-formed one naming an object that does not
exist exits 1, because that is a lookup failure and not a typo.

Declare only flags the check actually reads; the common ones (`--namespace`,
`-A`, `--workload`, `--format`, `--timeout`, …) come from `emit.CommonFlags()`
and must not be redeclared.

### 3.6 `Run`

The shape is always the same: list, judge in memory, sort, emit, note, return.

```go
func runNetpol(ctx context.Context, deps Deps, inv emit.Invocation) (int, error) {
	// … scope checks …
	client, err := deps.client(ctx)
	if err != nil {
		return 0, err
	}
	templates, err := listPodTemplates(ctx, client, listNS)
	// … more lists …

	var findings []emit.Finding
	for _, ns := range namespaces {
		findings = append(findings, judgeNetpolNamespace(ns.Name, templates, policies)...)
	}
	sortFindings(findings)
	for _, f := range findings {
		if err := inv.Out.Emit(f); err != nil {
			return 0, err
		}
	}
	if err := inv.Out.Note("namespaces", itoa(len(namespaces))); err != nil {
		return 0, err
	}
	return len(templates), nil
}
```

Four rules hide in there:

- **The judging is a pure function of listed objects.** `judgeNetpolNamespace`
  takes slices and returns findings. That is what makes the check testable
  without a cluster and what keeps the API calls in one place.
- **Output is sorted before it is emitted.** Unsorted map iteration produces a
  golden that fails one run in five.
- **The return value is what was EXAMINED, not what was found.** `scanned`
  is the denominator of the coverage claim — return `len(templates)`, never
  `len(findings)`. Getting this wrong is how a tool ends up implying it looked
  at a cluster it never listed.
- **Every finding carries a fingerprint.** Posture claims use
  `engine.PostureFingerprint(kind, reason, kindOfObject)` — deliberately
  class-level, so the same posture on 40 workloads dedups to one fleet fact.
  Incident claims use `engine.Fingerprint`, which is instance-level and frozen
  at schema v1.

## 4. Tests

Per §13, `fake.Clientset` fixtures and a fixed clock; no cluster, ever. A
check's suite has five kinds of test and the scaffold stubs all five:

1. **One exact assertion per defect.** Not "some finding fired" —  the kind,
   the severity, the reason, and the details that matter.
2. **A healthy fixture proving silence.** `findings=0` on a
   normally-configured cluster. This is the test that catches the check that
   fires on everything, and it is the one most often left out.
3. **A look-alike fixture proving the exclusion.** netpol has
   `TestNetpolHostNetworkIsOutsideThePolicyModel` and
   `TestNetpolNamespaceWithNothingToProtectIsSilent`.
4. **One golden over a mixed cluster** — `checktest.Golden(t,
   "testdata/netpol.golden", res.Stdout)`. Update it with
   `UPDATE_GOLDEN=1 go test ./pkg/checks/<group>`; that is the only update
   mechanism in the tree.
5. **The contract round-trip** — `checktest.VerifyContract(t, cmd, args...)`
   runs the command in both formats and re-parses the output against the
   declaration. This is what enforces the kind ledger and the output glossary,
   so it is not optional.

Scope errors get their own table test asserting `emit.ExitUsage`; a target that
is well-formed but names nothing gets one asserting `emit.ExitRuntime`.

## 5. The touchpoints

Nine, of which the scaffolder does five.

**Generated by `dev/tools/new-check`:**

1. `pkg/checks/<group>/<check>.go` — the command.
2. `pkg/checks/<group>/<check>_test.go` — the suite.
3. `pkg/checks/<group>/testdata/<check>.golden` — the first golden.
4. Registration — `checks.Register` in the group's `init()`.
5. The `Kinds` / `Output` skeletons.

**Yours, because a generator cannot decide them:**

6. **Scan membership.** `pkg/checks/scan/scan.go`: add the command to `stage1`
   (a bare `lookout scan` runs it) or to `excluded` **with the reason**. The
   coverage test `TestScanCoversEveryRegisteredCommand` fails until you choose,
   which is the point — a check nobody can reach is worse than no check.
   Commands in the opt-in groups (`audit`, `cloud`, `perf`) are covered by
   `optionalGroups` and need nothing.
7. **RBAC**, if the check reads an API resource nothing else reads. Add the
   verb to `deploy/12-clusterrole-watcher.yaml`; if the check goes through
   `state.LoadCluster`, declare the resource in
   `state.LoadClusterListRequirements` too. `pkg/checks/state/rbac_test.go`
   parses the manifest against those requirements and will tell you.
8. **Skills**, if a workflow should reach for the command. Add it to the right
   entry of `skilldoc.SkillCommands` and mention it in that skill's `SKILL.md`
   decision tree. A command no skill names is reachable by an agent that
   already knows it exists, and by no other.
9. **Docs**, regenerated in this order — `gen-site-docs` must run last or its
   output is stale:

   ```console
   $ dev/tools/gen-skill-refs
   $ dev/tools/gen-site-docs
   $ dev/tools/ci
   ```

Then a `CHANGELOG.md` entry under `## [Unreleased]`, which is not a touchpoint
so much as the house rule.

## 6. Adding a whole group

`new-check` refuses a group that does not exist, because a group is a bigger
decision than a check: it is a claim about a *class* of question. `audit` is
"nothing is wrong right now, and there is no safety net for when it is";
`triage` is "something is wrong right now". If a new check does not fit an
existing group's claim, say what the new group's claim is first, in the package
doc, and then:

- `pkg/checks/<group>/<group>.go` with the package doc, a `Deps` struct, its
  accessors, and `init()`.
- The group in `groupDocs` (`pkg/checks/command.go`) and in DESIGN §4.1 —
  `Validate()` rejects an unknown group, so this comes first.
- A blank import in `pkg/checks/all/all.go`. That is the *only* import site;
  `TestAllImportsEveryRegisteringPackage` walks `pkg/checks/**` for
  `checks.Register` and fails if the new package is missing.
- Scan's `stage1` / `excluded` / `optionalGroups`, per touchpoint 6.

## 7. Things that will bite you

- **Panics at init.** A `Register` panic surfaces as every test in the package
  failing before any of them run. Read the panic message; it names the field.
- **A stale golden in a *different* package.** Adding a check changes
  `lookout --help`, the MCP tool list, and both doc generators. `dev/tools/ci`
  catches all of it; running only your package's tests does not.
- **Lint findings pointing at a file that does not exist.** That is a stale
  shared golangci cache from another worktree. `golangci-lint cache clean`.
- **A check that needs a CRD.** There is no read-path pattern for
  discovery-gated CRD detectors yet (the sentinel has one, in
  `pkg/sources/gateway`). Open a design issue rather than inventing a second
  one.
